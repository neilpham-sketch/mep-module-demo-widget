# Demo Widget (`mep-module-demo-widget`)

Generated by the `mep` CLI (docs/ADR-0001). This repo is a pnpm workspace: `apps/internal`
+ `apps/external` (NestJS backend) + `packages/ui` (Next.js UI library, consumed by
`mep-dashboard-fe`).

## Backend: boot and verify in under 10 minutes (PRD §8 "Time-to-first-boot")

The backend (`apps/internal`, `apps/external`, `apps/worker`, `libs/`) is a single
Nest-CLI monorepo rooted at this repo's own root — there is no separate `cd` into a
nested folder. `apps/internal` owns this module's business logic; `apps/external` is its
public-facing counterpart, empty until you add customer-facing routes to it — both share
the same `libs/`:

```bash
pnpm install
cp apps/internal/.env.example apps/internal/.env
cp apps/internal/venv/.env.example apps/internal/venv/.env.dev
cp apps/external/.env.example apps/external/.env
cp apps/external/venv/.env.example apps/external/venv/.env.dev
pnpm db:generate && pnpm db:migrate
pnpm start:dev
```

Then check:

```bash
curl http://localhost:8080/demo-widget/api/v1/health
curl http://localhost:8080/demo-widget/api/v1/ping
```

`apps/external` boots the same way on its own port (`pnpm dev:external`, default
`8081`, health at `/demo-widget/ext/api/v1/health`).

The first call is the liveness check (`docs/PRD.md` §6 P0). The second is the example
endpoint — you should get a `{ "module": "demo-widget", "ok": true }` payload (wrapped
in the standard response envelope). Neither route is permission-guarded yet — wire up real
request-level authorization before this module handles anything sensitive.

## Setting this repo up on GitHub

`pnpm setup:github` (wraps `scripts/setup-github-repo.sh`) creates `mep-module-demo-widget`
under the org, pushes the `qa`/`staging` branches the deploy workflows trigger on, applies
branch protection (docs/ADR-0005 — PR-only), creates the `qa`/`staging` GitHub Environments
those workflows read from (`environment: qa` / `environment: staging` at the job level), and
sets the repo secret (`GH_TOKEN`) plus whichever per-environment secrets/variables
(`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, `SSH_PRIVATE_KEY_B64`, `INFISICAL_TOKEN`/
`INFISICAL_DOMAIN`, `MSTEAMS_WEBHOOK_URL` as secrets; `AWS_REGION`/`AWS_ACCOUNT_ID`,
`SSH_HOST`/`SSH_USER`, `HOST`, `INFISICAL_PROJECT_ID`/`INFISICAL_ENV` as variables) aren't
already set. Calls the GitHub REST API directly (curl) — nothing to install beyond `git`,
`curl`, and Node (already required by this repo).

Copy `.env.setup-github.example` to `.env.setup-github` and fill in `GITHUB_TOKEN` (a PAT
with the `repo` scope and org repo-creation rights) plus the `QA_*`/`STAGING_*`-prefixed
values for whichever secrets/variables aren't already set, then run `pnpm setup:github` —
`.env.setup-github` is gitignored and never committed. `git push` itself still uses whatever
auth you already have configured for github.com (SSH key or credential helper), not
`GITHUB_TOKEN`.

It does not provision the ECR repos, the Infisical project/secret paths, Kong route, deploy
hosts, or `mep-tenant` registration those workflows depend on — those are real infra, set up
once per module (docs/ADR-0004). Runtime config (`DATABASE_URL`, `RABBITMQ_URL`, ...) for the
deployed containers comes from Infisical at boot (each Dockerfile's `infisical run` wrapper
in `CMD`), not from any file in this repo — local dev still uses the plain `apps/*/venv/.env.*`
files above.

## Frontend: `packages/ui` has no login, middleware, or layout of its own

Unlike the backend, `packages/ui` cannot run standalone (docs/ADR-0011) — it is a route/
component library meant to be imported into a running `mep-dashboard-fe`. To preview it
locally during vibe-coding, either:

1. Run a local `mep-dashboard-fe` checkout and `pnpm link` this package into it, or
2. Build a minimal local harness page that wraps `<DemoWidgetPanel apiClient={...} />`
   with the same providers `mep-dashboard-fe` supplies (QueryClientProvider, an axios
   instance pointed at your locally-running `apps/internal`).

There is no "just run packages/ui" shortcut yet — this is a known, named gap (docs/ADR-0011
Consequences), not an oversight.

## Delivering this module to a tenant

Delivery is **staging/dev only** (docs/ADR-0005) — see `module.manifest.json` and the
platform's "Deliver to tenant" flow (docs/ADR-0004) in `mep-tenant`/`mep-fe-tenant-management`.
This repo alone does not deploy itself to any tenant.
